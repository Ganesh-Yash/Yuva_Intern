## Week 3 report description

This Week 3 report documents unsupervised learning and honest model evaluation on a 720-row employee sample that continues the HR schema from Weeks 1 and 2. Three latent career-stage segments were built into the data (early-career, mid-career specialists, senior high-performers) but hidden from the algorithms. K-Means was fitted on standardised age, tenure, salary and performance. Inertia (elbow) and silhouette scores were computed for k = 2 through 8; k = 3 was selected because it sits at the elbow, is at or next to the silhouette peak, and is the number of groups a business can actually name. Cluster means map cleanly onto those three personas. Agglomerative clustering with Ward linkage was then cut at the same k, and a dendrogram on a 60-row subsample shows the merge costs. Principal Component Analysis projects the four features onto two axes that retain most of the variance, so K-Means labels, hierarchical labels and the true generating segments can be compared on the same plane. PCA is used here as a visualisation, not as a step that discards features before clustering.

The second half of the report returns to attrition classification. Because the leave class is the minority, accuracy is treated as insufficient. Stratified 5-fold cross-validation, with MinMax scaling inside a Pipeline so fold statistics cannot leak, is reported for Logistic Regression, a Decision Tree, Random Forest and K-Nearest Neighbors as mean ± standard deviation of accuracy, precision, recall, F1 and ROC-AUC. Random Forest is then tuned with GridSearchCV on F1 over n_estimators, max_depth, min_samples_split and max_features, using the training split only. Default and tuned forests are compared on a held-out test set with confusion matrices and ROC curves. All figures and tables were produced by process_week3.py; the Word document is the required upload.

## Week 4 report / project description

This Week 4 capstone is a complete attrition-risk application rather than another notebook. train_model.py generates an 800-row employee table, wraps StandardScaler and OneHotEncoder with a Random Forest inside a single scikit-learn Pipeline, selects hyperparameters with GridSearchCV on F1, and scores the winner on a stratified hold-out set. The fitted Pipeline is written to disk twice: models/attrition_pipeline.joblib (what the server loads — the recommended sklearn format) and models/attrition_pipeline.pkl (pickle, as required). metadata.json records feature names, class labels and test metrics so the service can describe itself without the training script.

app.py is a FastAPI process bound to 0.0.0.0. POST /predict accepts a validated employee JSON body (age, gender, department, city, years of experience, monthly salary, performance score), runs the serialised pipeline, and returns the class label, P(leave), a Low/Medium/High risk band and a short recommended action. GET / serves an HR form that calls /predict with a relative URL, so it works behind a preview proxy and does not hard-code localhost. GET /presentation is an eight-slide capstone deck; GET /docs is OpenAPI; GET /health and GET /metadata support operations. Putting preprocessing inside the Pipeline is the deployment lesson: the API cannot skip scaling or scramble dummy columns relative to training. The accompanying Word report is the project documentation; the HTML deck is the presentation. Together with Weeks 1–3 this is a path from a messy employee table to a running machine-learning product.
